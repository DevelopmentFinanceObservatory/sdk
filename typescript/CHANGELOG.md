## [Unreleased]

## [0.6.0] - 2026-11-21

### Added

- `rank` takes `per`, a role or roles that split the ranking. `client.analysis.rank(aid, { by: "origin", per: "destination", limit: 6 })` keeps the six largest origins of each destination, each destination with its own ranks, ties and `limit`. It sends `partition_by`, and a recipe that made the dataset names the partition's column by the role word the call used. A `per` that is empty, not text, or names a role `by` names throws `InvalidRequestError` (`invalid_argument`) before any request.
- `aggregate` and `rank` take `allowSparseBreakdowns`. With `true`, DFO counts a year of a group as covered when any of its breakdown members, such as the purposes a summed CRS reading keeps, holds a row, where it would refuse `coverage_insufficient`. It sends `allow_sparse_breakdowns: true`, and nothing when left out or `false`, so a step without it keeps its ids. A value other than a boolean throws `InvalidRequestError` (`invalid_argument`) before any request.
- `dataset.statVarsSummed` lists each reading a recipe read summed over its StatVars, as the analysis answer's `stat_vars_summed` states it, each as `{ specId, contentVersion, count }`, where `count` is how many StatVars with rows DFO added into one series. DFO sums a reading of several StatVars by itself when no step names `stat_var`. The text form prints it as `Summed: 1,598 StatVars`, or `Summed: 1,598 and 40 StatVars in 2 readings` for two readings. It is empty for a recipe that summed nothing, for a derived ref read at its exact version, which posts no analysis, and for a saved file. The `SummedReading` type is exported from `@developmentfinance/client/types`. An answer whose list breaks that shape, or gives a `count` below 2, throws `ContractError` (`contract_violation`) at the pointer of the field it breaks, such as `/stat_vars_summed/0/count`.
- `client.fetch(recipe, { latest: "stored" })` runs a recipe on the version DFO stores as the newest of each reading it starts from. It reads each reading's manifest once, from `GET /datasets/{spec_id}` in the reading's rendering, all at once, downloads no root's file, and posts the recipe with those versions. A recipe of one reading makes four requests (the manifest, the analysis, and the computed frame's manifest and file), and each further reading adds one. A spec root reads its frame without party totals. A root of several members throws `InvalidRequestError` (`several_members`) before any request, the refusal DFO gives such a tree. `dataset.freshness` is the worst freshness those manifests state. A recipe with no step, or one that starts from a frame DFO computed, throws `InvalidRequestError` (`invalid_argument`) before any request, and when one manifest read fails the others are aborted. `RecipeFetchOptions` types `latest` as `boolean | "stored"`.

- A dataset a recipe made names the split of a partitioned ranking in its text form's `Derived` line, as `rank by origin per destination, limit 10`, with each column named by the role word the call used. A dataset that holds a partitioned ranking writes format 3 from `toBytes()`, which lets a step in `dfo.steps` carry `per`; any other derived dataset still writes format 2. `Dataset.fromBytes` reads formats 1, 2 and 3. It throws `FormatError` (`format_invalid`) at `/dfo.steps/0/per` for a `per` in a format 2 file, one that is not an array, is empty or repeats a column, one on a step that is not a `rank`, or one that names a column the step's `by` names, and at `/dfo.steps/0/per/0` for an empty column name. A recipe whose `partition_by` is present and is not a non-empty array of distinct strings, or that, once named by roles, would break one of those rules throws `ContractError` (`contract_violation`) when the dataset is built, so a file the client writes loads.

### Changed

- The contract follows spec-kit `a47d08d`, which maps `verify_not_permitted` to `PermissionDeniedError` and adds the analysis scenarios and format 3 of the saved-file schema.
- `recipe(new DatasetRef([]))`, a ref of no members, throws `InvalidRequestError` (`invalid_argument`) when the recipe is built. Before, the recipe posted the empty ref, and `latest: "stored"` threw a `TypeError`.

## [0.5.0] - 2026-11-20

### Added

- `client.fetch(ref, { latest: "stored" })` reads, for each member of a ref, the version DFO stores as the newest of the member's spec, in the member's rendering: `GET /datasets/{spec_id}` with the rendering as its query, then the file the manifest lists for that rendering, checked against its digest. It makes no Search call, and each member keeps the ref's sentence. A 202 is polled to the built version as a long build is, reporting to `onProgress`. `dataset.freshness` says how new the versions are, from each answer's `x-dfo-freshness` header: `"current"`, `"pending"` or `"stale"`, the worst of the members', `"current"` for a member whose read waited for a build, or null when any other answer states none, and for every dataset another fetch or a saved file returns. `dataset.ref` and the saved file leave it out. The `Freshness` type is exported from `@developmentfinance/client/types`. `latest: "stored"` on a spec, a recipe, a ref of a frame DFO computed or a share throws `InvalidRequestError` (`invalid_argument`) before any request, and `RecipeFetchOptions` and `ShareFetchOptions` refuse it at compile time. An answer for another spec throws `ContractError` (`contract_violation`).

## [0.4.1] - 2026-11-19

0.4.0 was tagged and never published. 0.4.1 is the first release on the registry with the 0.4.0 changes listed below it.

### Changed

- `hyparquet-writer` loads with a dynamic `import()` in `Dataset.toBytes()`, the only place the client writes Parquet. A bundler that splits dynamic imports leaves the writer out of the code a page loads to read a saved dataset. For an entry that calls `Dataset.fromBytes(bytes)` then `toRows()`, `esbuild --bundle --splitting --format=esm --minify --platform=browser` loads 117 KB (37 KB gzip) up front instead of 169 KB (52 KB gzip), and fetches the writer's 54 KB (16 KB gzip) only on a `toBytes()` call. A bundler that does not split inlines the chunk as before.

### Fixed

- A files route that answers the file with a 200 has its body read as a signed download reads one. The client's `attemptTimeout` bounds the wait for the response's headers, and the body then reads until the fetch's deadline, if any, failing with the retryable `network_error` once 30 seconds pass with no byte. Before, a 200 body had to arrive whole within the 30-second `attemptTimeout`, so a large file from a files route that answers 200 with the bytes timed out and was asked again.
- A fetch with `currency` and `facets` returned the reading in its own unit. 0.4.0 posted `facets` as the converted build's `scope`, which replaces the converted identity's whole facet binding and so dropped the unit request. `answer.fetch({ currency: "EUR", facets: { provenance: ... } })` returned the held spec, its sentence and its rows in current US dollars, with no warning or error. The converted reading now builds with no `scope`, since its identity holds the narrowing.
- A narrowed fetch in another currency converts the narrowed reading. The conversion request posts each reading's identity as `window`, `entities` and `facets` narrow it, so Search checks the rates for the years and places the build reads, and a narrowing to years the tables cover no longer throws `rate_coverage_gap` for years it leaves out. A refusal no longer suggests narrowing first and converting `ds.members[0].spec`.

## [0.4.0] - 2026-11-18

### Added

- `client.fetch(spec, options)` and `answer.fetch(options)` take `currency`, `priceBasis` and `baseYear`, named after the row columns they set, and fetch the reading in that unit: `answer.fetch({ currency: "EUR", priceBasis: "constant", baseYear: 2022 })`. `priceBasis` is `"current"` when left out, and constant prices need `baseYear`. The client posts one identity entry per answer part with the unit request to Search in one `dataset_resubmit`, each attempt waiting to the fetch's deadline, else 60 seconds, past the client's `attemptTimeout`, each with that part's operations, assumptions and `separate` flag, so a ranking such as "top 5 donors" and a declared default such as official development assistance carry over to the converted reading, and builds the converted readings, so the dataset's specs, sentences, `ref` and `provenance` are the converted ones. The conversion runs before `window`, `entities` and `facets` narrow a reading. `priceBasis` or `baseYear` without `currency`, a `currency` other than three capital letters, a `priceBasis` other than `"current"` or `"constant"`, a `baseYear` that is not an integer, missing for constant prices or given for current ones, `facets.unit` beside `currency`, and any of the three on a ref, recipe or share throw `InvalidRequestError` (`invalid_argument`) before any request. A reading Search does not convert throws the class `contract/actions.json` gives its reason, or `DfoError` with the reason as its code for one the contract does not list, such as `InvalidRequestError` (`rate_coverage_gap`) for a base year the tables do not cover, even under `partial: true`, with the missing rates in its message and in `problem.cause`; only Search's sentence in the message is cut at 1,000 characters, so the missing rates and any narrowing hint stay. A server refusal such as `recipe_not_declared` throws as any refusal does. A reply without one part per entry, or a converted spec that does not hold the request, throws `ContractError` (`contract_violation`). Each converted member carries the converted part's assumptions, departures and operations. Once a member is built, Search's `warn` and `degraded` warnings about it, such as `deflator_missing_omitted`, reach `onWarning` as `SearchWarning`s, each code once and none the member's manifest already issued, and `strict: true` throws the first before the artifact downloads. A narrowed build that Search names again for its sentence takes that reply's warnings, since the held reading's can speak of years and places the narrowing cut, and a second reading whose build is the same spec issues none of its own. That resubmit echoes the converted part's operations, assumptions and `separate` flag. A refused part's error and each `SearchWarning` carry the reply's trace id, its body's top-level `trace_id`, else its `x-dfo-trace-id` header. `Conversion` in `@developmentfinance/client/types` types the three options.
- `unitConversion(spec)`, exported from the root, reads the conversions a spec offers from Search's `resolved.unit_conversion`: a frozen `UnitConversion` of `currencies`, each a `ConversionCurrency` with `code`, `noun`, `currentYears`, `constantYears` and `baseYears` as `[first, last]` pairs or null, and `defaultBaseYear`. It returns null for a spec with no Search reading and for a series that converts to no currency, and throws `ContractError` (`contract_violation`) for an offer it cannot read. Both types are exported from `@developmentfinance/client/types`. `answer.toJSON()` keeps each spec's `resolved.unit_conversion`, so an answer read back with `Answer.fromJSON` offers the same conversions.

## [0.3.0] - 2026-11-17

### Added

- `client.search({ codes, ... })` takes publisher series codes in place of a question: `client.search({ codes: ["DT.TDS.MLAT.CD", "DT.TDS.BLAT.CD"], entities: { destination: ["country/KEN"] }, window: [2015, 2023] })`. Each code is its own part of the answer. `variable` gives words that choose among a code's variables and defaults to the code itself. `entities` and `window` take the forms `client.fetch` takes, `openRoles` takes `origin` or `destination` to answer member by member, and `source` names the source in words, such as `"IDS"`, for a code two sources hold. `CodeSearchOptions`, exported from `@developmentfinance/client/types`, types the object. A question beside any of these keys, an object without `codes`, `codes` as one string or naming a code twice, an open role that is not a string, or a second options object beside the codes throws `InvalidRequestError` (`invalid_argument`) before any request. A key set to `undefined` is absent. The client sets no cap on codes or entities. A server refusal arrives as `request_invalid`.
- An answer flags a part asked by a series code whose reading is not that code's series alone: every code in the spec's `resolved.stat_vars.source_codes` must be the asked code with `exact` true. Such a part keeps its reading and becomes a gap of kind `no_data` whose message names the asked code and the codes the reading holds, and says to narrow the search with `variable` or `source`, or to fetch the reading as it is with `client.fetch((answer.parts[i] as DefinitePart).spec)`. `answer.fetch()` throws `IncompleteAnswerError` (`answer_incomplete`), `answer.fetch({ partial: true })` builds the other parts, and `answer.choose` posts the part back by its restatement. In an answer to a search by codes, the code each part asked decides, whatever the part's restatement names or leaves out. `answer.toJSON()` writes such an answer at `format_version` 2, with those codes in a top-level `codes` member, one per part in part order, and `Answer.fromJSON` reads them, so an answer read back has the gaps the live answer had. An answer to a question in words stays at `format_version` 1. `answer.choose` keeps the codes too, so the new answer checks each part against its code again, and a reply to the choice with another number of parts than codes throws `ContractError` (`contract_violation`). `fromJSON` reads `codes` as `client.search({ codes })` reads them, and throws `FormatError` (`format_invalid`) at `/codes` for codes `search` refuses, such as a blank code or one code twice, for a count other than the parts, for `codes` at format 1, and for format 2 without them. 0.2.0 refuses format 2 as "not 1". Both clients trim a code of the white space JavaScript's `trim` removes, so a code reads the same in each. An answer to a question in words writes no `codes` and reads a part's code from its restatement, so the check holds for a code Search found in the question's words. A code part whose spec has no `resolved.stat_vars` is a gap too. Answer JSON written by 0.2.0 holds none, so a 0.2.0 saved answer whose question named a series code reads back with a gap on that part, and fetching it needs a fresh search. An incomplete answer whose every part names a series code counts series codes: "Answered 2 of 3 series codes."
- `client.fileUrl(member)` returns a link to a pinned member's file that a pipeline can commit and read with any HTTP client and no key. The member is one of `data.members` or `data.ref.members`. The URL names the file selector, `/datasets/{spec_id}/{content_version}/file`, under the client's base URL, with the query of the rendering the member was built in, so it serves the same table. The call reads the version's manifest once. A version that is not pinned throws the new `VersionNotPinnedError` (`version_not_pinned`) from `@developmentfinance/client/errors`, an `InvalidRequestError` whose `heldUntil` field is the date DFO stops guaranteeing the version and whose message says to run `client.pin(data)` first. A member of a derived dataset, or an object without a string `spec.spec_id`, a string `contentVersion` and a rendering of a known format and a boolean `bundle`, throws `InvalidRequestError` (`invalid_argument`) before any request.
- `data.provenance` is a `Provenance`, exported from the root, a frozen record of where a dataset came from: its sentence, citation, `fetchedAt`, question, `pinned`, `heldUntil`, warnings, `complete`, `missing` and members, each with its spec id, version, digest, parts, sentence, citation and retention, and `ref`, the `DatasetRef` the members name. `JSON.stringify(provenance)` writes it, through `toJSON()`, whose object `ProvenanceJson` in `@developmentfinance/client/types` types, in the format `provenance.schema.json` in the client contract gives. `Provenance.fromJSON(value)` reads a record either client wrote, from its JSON text or its parsed value, as `DatasetRef.fromJSON` does, and `provenance.equals(other)` says whether two records hold the same facts, as Python's `==` does. A key the format does not name, at the top level, in a member, in a citation or its sources, in a warning, or in a missing part or its options, is ignored, so a record a later client adds a key to still reads. The ref keeps its own format. The record's and the dataset's `pinned` and `heldUntil` come from the members' retention. `complete` and `missing` are the dataset's, each missing part as the saved file holds it, so a partial dataset's record differs from a complete one's. `Dataset.fromBytes` and `load` refuse a saved file whose `dfo.dataset` has a `complete` other than whether `missing` is empty, as the record's reader does, with `format_invalid` at `/dfo.dataset/complete`. A record that breaks the format, comes from a later `format_version`, has members that differ from the members its ref names, or a `pinned` or `held_until` other than what its members give, a record with no member included, or a `complete` other than whether `missing` is empty, throws `FormatError` (`format_invalid`) at a JSON Pointer, and a ref that breaks its own format throws as `DatasetRef.fromJSON` does, under `/ref`. `data.toBytes()` writes the same facts from the same record. A saved warning's `spec_id` comes from the record.
- Each of `data.members` holds its version's retention, `pinned` and `heldUntil`, as its manifest serves it, each null when the server does not say. `data.pinned` and `data.heldUntil` keep their meaning and derive from the members' values. A dataset is pinned when every member is, and held until the earliest date of the members not pinned. `client.pin(data)` returns a dataset whose members are all pinned. `data.toBytes()` writes the members' retention under a new top-level key, `dfo.retention`, which Python 0.2.0 ignores. A file without it, as one 0.2.0 wrote, reads every member as pinned when the file says the dataset is, and otherwise with `pinned` null, unknown, and the file's `held_until`. A file whose `pinned` or `held_until` is other than what its members give, a file with no member included, throws `FormatError` (`format_invalid`).
- `Dataset.fromBytes(bytes)` reads the file `data.toBytes()` and `data.save(path)` write, and the file Python's `data.save` writes, in any runtime, with its rows, provenance and ref, and `load(path)`, exported from the root, reads one from a path on Node. It is a port of Python's saved-file reader and refuses what it refuses with the same codes: bytes that are no Parquet file, a damaged one, or one without a saved dataset's `dfo.*` keys throw `BundleError` (`not_a_bundle`), exported from `@developmentfinance/client/errors` with `BundleErrorReason`, and a `dfo.*` key that is missing, breaks the saved format or comes from a later format version throws `FormatError` at a pointer that starts with the key. The reader checks the `dfo.*` keys, then the footer's row count against its row groups and against what the file's bytes can hold, before it decodes a row, so a small damaged file that declares a billion rows throws `BundleError` (`not_a_bundle`) at once. A file of more than 16,777,216 rows throws `BundleError` (`not_a_bundle`) before any decode. Python's `dfo.load(path)` reads it. A file of several members holds them in one table, `part` first, split by `dfo.dataset.member_rows`; the loaded dataset's `memberBytes` throws `InvalidRequestError` (`invalid_argument`), and its other conversions, `String(data)`, `provenance` and `ref` work as on the dataset that wrote it, so `Dataset.fromBytes(await data.toBytes())` writes the same file again. The file keeps no record of the role words a recipe's call named its columns by, so a loaded derived dataset's `leftOut` series print DFO's column names, such as `financingRecipient` for `destination`, as Python's `dfo.load` prints them. In a browser, `load(path)` throws `InvalidRequestError` (`invalid_argument`) naming `Dataset.fromBytes`.

### Changed

- `data.heldUntil`, each member's `heldUntil` and `VersionNotPinnedError.heldUntil` hold the date the server names, at midnight UTC, as Python's `held_until` does and as a saved file keeps it. 0.2.0 kept the time of day, so a fetched dataset and its saved copy disagreed.
- `client.lookup.errorCode` replaces `client.lookup.code` for the registry entry of one of DFO's own error or warning codes, so the name no longer reads as a lookup of a publisher's codes. `client.lookup.code` stays as a deprecated alias that returns the same `Code`, carries a `@deprecated` tag, and reports a `DfoDeprecationWarning` (`name_deprecated`) to `onWarning` once per process, naming `lookup.errorCode` and 0.4.0, the release that removes it. Calls to `errorCode` that pass an unknown option name `client.lookup.errorCode` in the error.
- `answer.toJSON()` keeps each spec's `resolved.stat_vars.source_codes`, which the exact-code check reads.
- An answer counts and builds only the parts without a gap: `answer.specs` and `answer.fetch({ partial: true })` leave out a definite part that is a gap, and the printed answer counts it as missing.
- Breaking: `data.fetchedAt` is `Date | null`. It is null on a dataset read from a file with no fetch time, such as one Python saved from a website bundle. A fetched dataset always holds a time.
- `data.ref` on a dataset read from such a file, which names no version, throws `InvalidRequestError` (`ref_unavailable`), as Python's `Dataset.ref` does, and `String(data)` then leaves out the versions and ends `Keep: await data.toBytes()`. `client.pin(data)` on such a dataset throws `InvalidRequestError` (`invalid_argument`) before any request, as Python's `client.pin` does.

### Fixed

- A manifest warning keeps its `spec_id`, so `data.warnings`, `data.provenance` and a saved file record the spec it names, as Python records it, where the client wrote `spec_id: null`.

## [0.2.0] - 2026-11-14

### Added

- `data.partyTotalsLeftOut` names the group totals a fetch left out of each member, as `PartyTotalsLeftOut` entries of spec id, party role, dcids and provenance, and `String(data)` counts them. `data.toBytes()` writes them under a new `dfo.party_totals_left_out` key, which Python's `dfo.load` reads and its 0.1.0 release ignores.
- `PartyTotalsLeftOut` gives `keptIn`, the series whose rows kept an entry's totals, each a `KeptSeries` of its `series` cells and the `timePeriods` where the totals stayed, and `roleKey`, the `origin` or `destination` key a caller names the role by, or null for a column the client does not know. `KeptSeries` is exported from `@developmentfinance/client/types`. `data.toBytes()` writes `kept_in` where an entry holds it. A trace entry with an empty role, entity or period, or whose `kept_in` is malformed or out of the contract's order, is dropped, and the entries beside it still read.
- A derived dataset's `partyTotalsLeftOut` names the totals each root's read left out, from the derived manifest's `roots[].party_totals_left_out`, under the root's spec id and in the order of the ref's roots. Each ref root pairs with the served root of the same spec id and content version, and a served root that pairs with none is skipped. `String(data)` prints them as `Party totals left out of the readings`. The array is empty when the reads left nothing out, against a server older than this report, and when the server could not read a root.
- `answer.facts` gives each part's assumptions, departures, requested operations and warnings as typed `PartFacts`, one entry per part in the order of `answer.parts`, with a candidates part's `readingAssumptions` by spec id. `partFacts(part)` reads one part, and `PartFacts` is exported from `@developmentfinance/client/types`.
- The `attemptTimeout` client option bounds one request attempt, 30 seconds by default, as `timeout` did before. `client.withOptions` takes it too, and takes `timeout: null` to clear the client's `timeout` so each call keeps its own default.
- A role in `entities`, for `client.fetch` and `answer.fetch`, takes the resolved `Match` and the `Entity` objects `client.lookup.resolve` returns, read as their dcids with no request. A `Match` that did not resolve throws `InvalidRequestError` (`match_unresolved`) before any request, naming the dcid of its first candidate, else of its nearest match.
- `SpecFetchOptions`, `RefFetchOptions`, `RecipeFetchOptions` and `ShareFetchOptions` type each target's options, and `EntityChoice` a role's entry in `entities`.
- `data.save(path)` writes the file `data.toBytes()` returns, on Node. Outside Node it throws `InvalidRequestError` (`invalid_argument`) naming `toBytes()`.
- `data.question` holds the question a dataset fetched from an answer answers, else null, and `data.fetchedAt` the time the data left the server, to the second. A saved file keeps them under two new top-level keys, `dfo.question` (absent when there is no question) and `dfo.fetched_at`, each a JSON string, the time in UTC ISO 8601 such as `"2026-11-13T09:15:42Z"`. Python's 0.1.0 `dfo.load` ignores both.
- `data.licence` joins the licences the sources publish under with "; ", as Python's `Dataset.licence` does.
- `docs/settings.md` lists every client option and environment variable with its default and precedence.
- `DFO_TIMEOUT`, in seconds, and `DFO_MAX_RETRIES` set `timeout` and `maxRetries` for a client built without them, where the platform has a process environment. An option wins over the variable and leaves it unread. `timeout: null` on the constructor sets no client bound, so each call keeps its own default whatever `DFO_TIMEOUT` holds; it threw `InvalidRequestError` before. An invalid variable throws `InvalidRequestError` (`invalid_argument`) when the client is built, naming the variable. `client.withOptions` reads neither.

### Changed

- A fetch posts the party-totals cut, its default, as `party_totals: false` in the build request's `options`, the spelling DFO's API takes from dfo-apis 133262c5e on, in place of `without_party_totals: true`. Release 0.2.0 needs a server that accepts `options.party_totals`, and the release workflow checks that production does before it publishes. `DatasetRef.fromJSON` and a served rendering read either spelling, and `ref.toJSON()` still writes `without_party_totals: true`, so 0.1.0 reads a ref this release writes. The client follows the API contract at spec-kit 7ef7f71.
- A citation source's licence reads from the served `licence` and `licence_url`, falling back to `license` and `license_url` when the response lacks them, as a response from a server before the rename does.
- A fetch reads `trace.party_totals_left_out` leniently. A trace that is no object or a member that is no list names no totals, and a malformed entry is dropped while the entries beside it still read. A manifest with a broken trace no longer raises `ContractError`.
- Breaking: an error's message ends `[<code> trace=<id>]`, or `[<code>]` with no trace id, in place of `[<code> · trace <id>]`. The bracket's text may change between releases, so read `error.code` and `error.traceId` in code.
- Breaking: every error a public call throws is a `DfoError`. `FormatError` extends `DfoError` and no longer `TypeError`. Its `code` equals its `reason`, and its `reason` and `pointer` name the fault.
- Breaking: a secret `dfo_k_` key in a browser throws `InvalidRequestError` (`invalid_argument`) in place of `TypeError`. So do `new DatasetRef` given dataset and derived members together, `data.memberBytes(index)` past the last member in place of `RangeError`, and `data.toRows()` on an INT64 value beyond a JavaScript number's exact range in place of `RangeError`. `RawResponse.json()` on a body that is not JSON throws `ContractError` (`unexpected_response`) in place of `SyntaxError` or `TypeError`.
- Breaking: the client's `timeout` option bounds a whole call, retries, build waits and downloads included, and a call's own `timeout` replaces it. Unset, each call keeps its own default: `search` and `answer.choose` stop after 60 seconds, and `fetch` waits as long as the build takes. Code that set `timeout` to bound one attempt sets `attemptTimeout` instead.
- Breaking: the `timeout` of a lookup and of `client.request` bounds the whole call, retries included, in place of one attempt.
- Breaking: `client.fetch` has one overload per target, so `tsc` refuses an option the target does not take: `latest`, `asOf` or `slot` with a spec, a narrowing or `partyTotals` with a ref, a recipe or a share, `onProgress` or a layout other than `frame` with a recipe, and `latest` or a layout other than `frame` with a share. A target typed as a union of kinds takes `signal`, `timeout` and `strict`. The run-time checks are unchanged.
- Breaking: `data.bytes()` is `data.toBytes()`.
- Breaking: `CitationSource`, the type of `data.citation.sources`, is the client's own: `ref`, `label`, `licence`, `licenceUrl` and `url`, with null for a field the source leaves out. It spells the licence as Python does in place of the server's `license` and `license_url`, and drops the server's other fields. The server's type stays in `@developmentfinance/client/wire`. Saved files keep their keys.
- Breaking: a part in `answer.parts`, and the `Part`, `KnownPart`, `DefinitePart`, `CandidatesPart`, `NoDataPart`, `UnsupportedPart` and `UnknownPart` types `@developmentfinance/client/types` exports, types only the members the client checks: `status`, a definite part's `spec`, a candidates part's `candidates.specs`, a no-data part's `no_data.reason` and an unsupported part's `unsupported.code`, and within each spec its `spec_id`, `definition.spec_id`, `definition.identity` as an object and `resolved` as an object. Every other member, `assumptions`, `departures`, `operations`, `warnings`, `variable_text` and every member of a spec's `resolved` among them, is `unknown`. Read those from `answer.facts`. `@developmentfinance/client/wire` keeps the schema types.
- Breaking: the `resolved` of a `Spec`, as `answer.specs` and `candidate.spec` hold it, types its members `unknown`, since the client does not check them. `ResolvedSpec` in `@developmentfinance/client/wire` keeps the schema type.
- Breaking: `isKnownPart` is true only for a part that holds the members the client checks for its status, as JSON types, in place of any part with a known `status`. Every part of an answer from `client.search` with a known status passes.
- Breaking: `QueryOption`, a refusal's choice in `gap.options`, is now `Option`, the name the Python client uses.
- Breaking: the package root exports `Client`, `Answer`, `Dataset`, `DatasetRef`, `Spec`, `recipe`, `latestYear`, `VERSION` and `ClientOptions`, the names Python's `dfo` holds at its top level, in place of 160 names. The errors, the warnings, `isDfoError` and the types their fields carry move to `@developmentfinance/client/errors`, as in Python's `dfo.errors`. Every other name moves to `@developmentfinance/client/types`, as in Python's `dfo.types`: the types answers, datasets, cards, shares and lookups contain, the option types, the `Analysis`, `Cards` and `Lookup` classes, `ApiKey`, `RawResponse`, and the helpers `specRoles`, `partFacts`, `isKnownPart`, `PART_STATUSES`, `isDatasetMember` and `isDerived`. - Breaking: the `withoutPartyTotals` and `without_party_totals` options get the generic unknown-option refusal, in place of a hint that names `partyTotals` and its default.

## [0.1.0] - 2026-11-13

The first release of `@developmentfinance/client`, the TypeScript client for the Development Finance Observatory APIs. It is ESM only and runs on Node 22.18 or later, Bun, Deno, Workers, and browsers.

### Added

- `client.search(question)` returns an `Answer` whose text form is Search's sentence and the next call to make. `answer.choose(option, { part })` settles a part that awaits a choice, and `answer.fetch()` and `client.fetch(spec)` return a `Dataset`, narrowed with `window`, `entities` and `facets`.
- `data.ref` names the exact versions a dataset holds. `client.fetch(ref)` reads them again, and `client.fetch(ref, { latest: true })` builds the newest. Refs and the Parquet file from `data.bytes()` are shared with the Python client.
- `client.lookup` resolves names, reads graph nodes and codes, and lists what Search holds data on.
- `client.analysis` runs DFO's operations on the server and returns a derived `Dataset`: `filter`, `aggregate`, `growth`, `rank`, `quotientOf`, `shareOf`, `join`, `sumOf` and `compare`, each with `strict`, `timeout` and `signal`. `growth` with `change: "relative"` is a fraction where 0.25 is a 25% rise and `change: "difference"` is in the data's unit, and `shareOf` is a percentage.
- `recipe(start)` describes a chain of operations without running it, and `client.fetch(recipe)` runs it in one request. `latestYear(offset)` names a year DFO settles each run. `client.fetch(ref)` reads a derived ref, and `client.fetch(ref, { latest: true })` computes it again on the newest data.
- `Dataset.leftOut` lists the series an operation dropped for missing data, with the step and the reason, and `SeriesLeftOutWarning` (`series_left_out`) says so once per fetch, thrown under `strict: true`. A derived dataset's text form names its steps, the period `latestYear` settled on, and the count of series left out. The file from `data.bytes()` declares format version 2 for a derived dataset, which a client that reads format 1 alone refuses as a later format, and format 1 for a dataset of dataset versions. `isDatasetMember(member)` and `isDerived(member)` narrow a member of a dataset or a ref, so a dataset member's `spec` passes to `client.fetch`.
- Each `Root` of a derived member names the rendering the recipe read it in, and `groupby`, a `Groupby` of `by`, `op` and `levels`, when the recipe read it summed, as a breakdown or a sum over StatVars does. The ref keeps it through `JSON.stringify`, `DatasetRef.fromJSON` and `data.bytes()`.
- `client.pin(data)` keeps a dataset's versions fetchable with no time limit.
- `client.cards` stores `line`, `bar`, `table`, `stat` and `source` cards of a dataset. `stat` with `change: "percent"` is a percentage where 25 is a 25% rise.
- `client.share(cards, { latest })` publishes cards at a public URL that follows new data or keeps today's versions, and returns its `shw_` write token. `replace`, `client.snapshot` and `client.unshare` change it with the token, and `client.history` lists what each slot served.
- `client.fetch(share, { slot, asOf })` returns the data a share's slot shows, or showed on a date. A slot whose version lists no frame-layout file, as a default fetch leaves it, reads the file the version's file selector renders from its stored frame.
- Errors derive from `DfoError`, one class per next step, and each message ends with its code, and with the trace id when there is one. The client retries failures that can clear, honouring `Retry-After`.
